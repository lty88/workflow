# 主数据独立保存与版本设计（2026-10-23）

## 为什么调整

原系统以configuration的整包JSON为主，发布时物化members、departments等表。导致手动清空members仍能显示人员、组织编辑必须发布、配置页面无法清晰知道是否已提交。

调整后，人员、部门、角色、菜单均以对应业务主表为唯一运行来源；CompanyConfig只作为服务端装配的领域上下文，不是数据库主数据。配置页面的编辑副本仅存在浏览器内存，按模块保存后直接生效。

## 数据库职责

| 表 | 职责及约束 |
| --- | --- |
| members | 人员、唯一登录名、所属部门、active、角色ID集合、scrypt密码。列表、登录和运行权限统一从此读取，接口不返回密码。 |
| departments | 部门树、负责人、启停状态；读取真实列，忽略旧data副本。负责人必须属于本部门。 |
| roles | 角色名称、权限与数据范围、页面授权。可变权限集合保留JSON定义，不再存入configuration。 |
| menu_pages | 动态菜单定义、启停状态、sort_order排序。 |
| menu_groups（新增） | 分组主数据及顺序。 |
| form_definitions（新增） | 当前表单定义与修订号。动态字段使用JSON描述，无整包发布步骤。 |
| form_definition_versions（新增） | 每次保存自动追加不可变的表单修订，联合主键(form_id,version)。 |
| workflow_templates | 工作副本、当前启用版本及并发修订号。允许未完成的流程设计先保存。 |
| workflow_template_releases | 启用时冻结流程定义和表单快照，按(template_id,version)唯一。 |
| activities及workflow_* | 活动实例与审批记录，继续保留提交时快照，不受后续模板修改追溯改写。 |
| configuration | 过渡期兼容行锁、技术修订号、表单ID及旧基础流程。第六版迁移后剥离users、departments、roles、pages、groups，不再作为主数据来源。 |
| configuration_releases | 旧发布历史，只保留历史用途，不用于恢复当前主数据。 |
| master_data_migration_backups（新增） | 保存第六版迁移前的完整发布配置和草稿，便于人工核对迁移前状态。 |

JSON仅承担动态定义或集合，人员和部门真实实体及其当前状态落在主表。旧data、roles等兼容列此次保留，避免破坏已有数据库工具；部门和人员显示读取规范列。跨实体关系由同一事务内的领域校验检查，包括树环路、负责人、角色与菜单引用、系统字段、历史身份、管理员交接及模板的部门/角色引用。

不通过关闭外键或级联清空活动解决人员删除。已有审批身份采用停用；当前页面可直接保存停用状态。手工物理删除成员会立即影响显示、登录与权限，不会从配置JSON自动补回。

## 前端与接口

| 页面 | 操作 | 接口 |
| --- | --- | --- |
| 组织架构 | 编辑部门/人员 → 抽屉保存 → 成功关闭，立即生效 | PUT /api/settings/organization |
| 角色权限 | 编辑授权 → 保存角色权限 | PUT /api/settings/permissions |
| 菜单页面 | 编辑页面/分组 → 抽屉保存，删除及其他批量修改点击页面保存 | PUT /api/settings/menus |
| 动态表单 | 编辑字段 → 抽屉保存；删除字段等修改点击页面保存 | PUT /api/settings/forms |
| 模板设置 | 修改名称、适用类型、范围等 → 保存模板设置，立即提交服务器工作副本 | 原模板保存接口 |
| 流程设计 | 保存修改 / 启用版本 | 原模板保存、发布接口 |

设置接口body统一为{changes,expectedRevision}，但changes按模块严格校验，只接受模块允许的字段；不接受任意整包覆盖。服务端锁定技术修订号并比较，冲突返回409，事务失败整体回滚。角色/菜单变更保存后刷新当前身份与菜单；其他会话请求时读取最新主数据。接口错误时保留抽屉和编辑输入。

GET /api/config暂时保留为管理员聚合读取接口，返回的published/draft兼容字段是同一份实时装配数据，不存在可单独发布的草稿。旧PUT /api/config/draft及POST /api/config/publish返回410，防止旧客户端再次写回整包JSON。

## 保存与启用的产品含义

- 组织、角色、菜单：保存就是提交接口并生效，不需要草稿和发布按钮。
- 表单：保存更新当前定义，同时自动保留修订记录，不额外要求发布。已有活动及已启用流程版本继续使用冻结表单。流程希望采用最新表单时，在流程设计器启用新版本。
- 流程：保存允许只完成部分设计，不要求立即替换运行版本；启用前检查完整结构、受理资格和默认推荐冲突。新申请采用启用版本，在途实例保持原快照。
- 模板设置：抽屉中现在有明确的保存按钮，可以单独提交服务器，不必先点击启用版本。设置属于整个流程定义的一部分，其保存不会跳过流程启用校验。

技术修订号仅防止多人覆盖，不要求业务人员执行“版本发布”。

## 迁移与操作顺序

本次只修改代码和迁移程序，未连接数据库执行。

1. 停止旧服务，备份整个数据库。
2. 如果members已被误清空：优先恢复数据库备份；也可显式执行`pnpm db:recover-members`，仅在第六版迁移前按旧发布配置插入缺失账号，恢复账号初始密码123456，已有账号和密码不改。该命令不会自动运行。
3. 执行`pnpm db:migrate`。第六版保留members现状，不从旧JSON自动复活被删除人员。缺少有效管理员会明确停止。
4. 重新启动服务与重新登录，使用模块保存。迁移前未提交的整包草稿保存在备份表，不自动合入主数据。
5. 之前交付的“真实组织架构-20261023”旧整包重置SQL仅适用于第六版之前，升级后禁止再用；该脚本已增加版本阻止条件。如需要导入该批组织，请在第六版升级前完成恢复与导入。

已安装第六版后，重复迁移不会重置成员密码、不会复活成员、不会覆盖当前表单。新库db:init会按顺序执行全部迁移。

## 验收清单

1. 清空某个测试人员主表记录后，重新请求人员列表不再出现；旧会话失效且登录失败。
2. 编辑人员姓名并在抽屉保存，刷新页面与members表一致；无“发布配置”步骤。
3. 停用人员但其仍为有效部门负责人时，接口拒绝并保留输入；应先更换负责人再停用。
4. 普通人员和无权限请求不能提交设置；当前管理员不能撤销自身管理资格。
5. 两窗口读取同一修订号，一个保存后另一个返回409，不覆盖先前修改。
6. 表单保存产生修订记录，旧活动和旧流程版本表单保持原样。
7. 模板设置点击保存后确实发出接口请求，刷新后设置保留；只有启用版本才影响新申请。
8. 旧配置接口返回410，旧种子整包入口和物化函数禁止在第六版后重写主表。
