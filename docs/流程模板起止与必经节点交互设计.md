# 流程模板起止与必经节点交互设计

日期：2026-10-22。交付状态：产品设计与独立可点击原型，正式应用代码及审批策略保持现状。

原型：`prototype/流程起止与节点规则原型.html`。

## 一、当前实现核对

### 1. 执行方向由依赖决定

默认布局方向是纵向从上到下，可以切换横向从左到右。箭头 A → B 表示 B 需要等待 A 完成；把 B 拖到 A 上方仅改变坐标，不会让 B 先执行。真正的顺序由前置节点决定，修改顺序应使用前插、后插或调整依赖。多个无前置节点在提交后同时进入；多个前置全部完成后才进入后续必办节点。知会不阻断，条件未命中时跳过并继承有效前置。

### 2. 默认节点是受保护的审批节点

服务端创建空白模板时写入：

- 名称：部门初审，可修改名称。
- 类型：审批；多人受理时采用全员通过。
- 默认前置：空，即提交后进入。
- 受理规则：申请人所在部门负责人，提交时根据申请人实际部门解析。
- 保护标记：必要审核；不能删除、改成任务或知会、设置条件跳过，不能改变已有受保护节点的受理规则。
- 当前仍可编辑：名称、前置关系、数据权限，图上位置也可移动。

改名为“研发部门内部初审”只改变显示名称，不会把受理人绑定到研发部门。推荐使用“申请部门负责人审核”，避免其他部门复用模板时误解。

“初审”是业务名称，“审批”是节点类型，“必要审核”是保护策略，三者必须分开呈现。

### 3. 必经与第一步有区别

目前程序要求每份模板包含无条件的、受保护的部门负责人审批，同时保护已发布版本中的必要节点，但没有强制该节点必须始终无前置。当前允许在它前面插入其他节点，也允许别的节点与它同时启动。它表示本轮审批完成前必须办理，不表示所有其他节点都必须等它完成。

这是本项目目前预设的治理规则，不是 G6 或所有流程引擎的技术要求。要支持不需要部门负责人审批的活动，应显式调整公司的必要审核策略及服务端校验；不能仅把前端禁用框解锁。

### 4. 当前缺失的表达

设计器有意过滤了“提交申请”“审批完成”等展示阶段，只保留可编辑业务节点。新手因此看不到边界，容易把默认部门初审当成开始节点；属性面板用禁用控件表达类型锁定，却没有完整说明受理人是谁、哪些属性仍能改。

实现核对位置：

- `apps/server/src/services/template-service.ts`：新模板创建、发布保护。
- `packages/domain/src/templates.ts`：必要部门负责人审核校验。
- `packages/domain/src/workflow.ts`：依赖激活与审批完成条件。
- `apps/web/src/components/templates/TemplateNodeInspector.vue`：属性开放与禁用范围。
- `apps/web/src/components/templates/editor-model.ts`：目前只展示真实业务节点。

## 二、推荐设计

### 1. 新建后明确出现三种对象

```text
开始 · 提交活动申请       系统节点，提交成功后自动触发
          ↓
申请部门负责人审核       审批节点，必经规则锁定
          ↓
审批结束                 系统节点，全部必办节点完成
          ↓
指派执行 → 活动执行 → 执行汇报 → 成果归档
```

“审批结束”不等于活动完成，也不覆盖退回、拒绝、取消等异常终止路径。执行、汇报、归档继续属于活动闭环，由当前服务端状态机负责。

开始与审批结束是图上的系统展示锚点，不加入真实审批节点数组、不分配待办、不增加审批轮次、不影响模板节点数量限制。与起点相连的无前置业务节点同时启动；结束锚点汇总所有必办分支。知会使用虚线，不能被误读为必须办理的完成门槛。

### 2. 用类型标签和锁定原因替代不明禁用

| 对象       | 卡片标记        | 点击后的属性说明                             | 可编辑内容                   |
| ---------- | --------------- | -------------------------------------------- | ---------------------------- |
| 开始       | 系统 · 开始     | 申请人提交成功后自动触发                     | 说明只读                     |
| 受保护审批 | 审批 · 必经     | 公司当前规则要求，无条件由申请部门负责人审核 | 名称、前置、数据权限         |
| 普通审批   | 审批 · 可配置   | 收集审批意见，多人全员通过                   | 名称、受理、前置、条件、权限 |
| 办理任务   | 任务 · 可配置   | 要求补材料、设计、印刷准备等实际办理         | 同上                         |
| 知会       | 知会 · 不阻断   | 到达触发时点后通知相关人员                   | 同上，明确不阻断             |
| 审批结束   | 系统 · 审批结束 | 必办分支完成，进入指派执行                   | 说明只读                     |

受保护节点的类型与受理规则用只读信息行展示，并附“公司规则锁定”说明；名称、前置和数据权限继续提供正常编辑入口。每个锁定字段给出对应原因，不能只出现灰色下拉框。

### 3. 编辑顺序要有明确语义

- 拖动：调整位置；保持箭头和执行顺序。
- 自动排列：按现有依赖整理并对齐；保持审批顺序。
- 前插审批或任务：新节点先完成，所选节点再进入。
- 后插审批或任务：所选必办节点先完成，新节点接入其后。
- 并行：新节点与参考节点具有相同前置，后续必办节点等待所需分支完成。
- 知会：单独说明其通知时点和不阻断性质；图上虚线与普通依赖区分。

在画布持续显示“位置不决定顺序，请按箭头阅读”；在前插、后插、并行按钮旁显示所选参考节点，减少上下坐标带来的误解。

## 三、版本与必要审核策略

近期先保留当前必要部门初审规则，完善展示与说明，不直接放开保护。新建最小模板默认把它放在开始之后。

后续如业务确认不同活动需要不同必要审核，增加公司级“必要审核策略”：由授权配置管理员维护适用活动类型、受理规则、是否要求作为第一关；模板设计器仅执行策略并展示原因。策略变更生成版本，发布前校验，新提交采用新版本；在途活动保留原快照。要校验“第一关”应检查依赖，而不是节点数组下标或画布纵坐标。

关键业务待确认：部门负责人审核是否适用于所有活动类型；是否允许预算复核、资料准备等节点先于它或与它并行。两项结论决定下一步是否需要调整业务策略，当前原型按已有程序允许的依赖关系演示。

## 四、独立原型评审范围

原型使用本地 G6，提供最小流程、完整示例、横纵切换、拖动布局、自动排列、前插/后插/并行、节点选择、名称和前置编辑、删除与撤销，以及系统节点和必要节点的锁定说明。原型仅使用演示数据，不连接账户、组织或数据库；普通节点的受理人和数据权限展示只表达设计意图，不执行真实授权。

评审步骤：

1. 最小流程中分别点击开始、必要审核、审批结束，核对类型与可编辑范围。
2. 在必要审核前插办理任务，确认它仍必经但不再是第一步。
3. 添加并行审批，核对共用前置和后续汇合提示。
4. 拖动业务节点到上方，核对箭头、前置和阅读顺序不变；点击自动排列恢复规整。
5. 修改必要节点名称，确认受理规则仍是申请人所在部门负责人。
6. 删除普通节点并撤销，确认必要节点和系统锚点不能删除。
7. 切换横向，检查顺序表达仍然一致。
